Страница описывает ключ, которым CRANE шифрует секретные настройки в таблице `setting` PostgreSQL. Ключ задаёт {{< env "CRANE_SETTINGS_KEY" >}} или файл {{< env "CRANE_SETTINGS_KEY_FILE" >}}: это base64 от 32 байт, ключ AES-256-GCM. Без ключа секреты в PostgreSQL не записываются и не читаются.

Сейчас сервер читает слой настроек в PostgreSQL при старте, но не имеет интерфейса, который записывает в него настройки (см. {{< xref "configure#stored" "Настройки в PostgreSQL" >}}). Поэтому сейчас ключ нужен, только чтобы открыть зашифрованные строки, которые уже есть в таблице. Переменная необязательна.

## Перед началом {#prerequisites}

- Постоянный каталог `postgres://`. При каталоге `memory` ключ — ошибка запуска.
- Команда `openssl` для примера ниже; подойдёт любой генератор 32 случайных байт.

## Шаги {#steps}

1. Создайте ключ и сохраните его в файле. Перевод строки в конце файла сервер отбрасывает; пробелы в ключе недопустимы.

   ```bash
   umask 077
   openssl rand -base64 32 > ./secrets/settings_key
   ```

2. Передайте серверу путь к файлу. Ключ задаётся ровно одним способом.

   ```ini
   CRANE_SETTINGS_KEY_FILE=/run/secrets/settings_key
   ```

   В файле TOML допустим ключ `settings_key_file`. Ключ шифрования читается только из окружения и файла: слой PostgreSQL его не задаёт.

3. Перезапустите сервер.

> [!IMPORTANT]
> Потерянный ключ восстановить нельзя: секреты, запечатанные им, не расшифровываются. Храните ключ отдельно от резервных копий PostgreSQL, иначе копия и ключ вместе раскрывают секреты.

## Проверка {#verify}

Сервер проверяет ключ при старте и называет проблему, не цитируя содержимое: в сообщении есть только длина. Тексты на русском языке. Примеры идут по порядку: не base64, неверная длина, ключ при каталоге `memory`, ключ вместе с файлом.

```text
CRANE_SETTINGS_KEY: ключ шифрования не является base64 (standard, с выравниванием, без пробелов)
CRANE_SETTINGS_KEY: ключ шифрования после base64 занимает 31 байт, нужно ровно 32
CRANE_SETTINGS_KEY: ключ шифрования не нужен при memory
переменные CRANE_SETTINGS_KEY и CRANE_SETTINGS_KEY_FILE взаимоисключающие
```

Успешный старт без этих сообщений подтверждает, что ключ принят.

## Как это устроено {#mechanism}

Секрет хранится как `nonce (12 байт) ‖ шифртекст ‖ тег (16 байт)`. Шифртекст привязан к имени настройки, номеру версии строки и отпечатку ключа, поэтому шифртекст, перенесённый в другую строку или оставшийся от старой версии, не открывается. Отпечаток — первые 8 байт SHA-256 от ключа в шестнадцатеричном виде (16 символов); по нему ключ не восстановить. Строка хранит отпечаток ключа, которым запечатана.

## Нечитаемые строки {#unreadable}

Если секретная строка в PostgreSQL не открывается, сервер не стартует и не подставляет значение по умолчанию: это поведение {{< term "fail-closed" "fail closed" >}}. Исключение — настройка, уже заданная окружением или файлом: её строка в PostgreSQL не используется и не расшифровывается. Сообщение называет настройку и причину, значения в нём нет. Причины:

```text
настройка `token` в БД не читается: задайте CRANE_SETTINGS_KEY: строка запечатана, а ключа нет
настройка `token` в БД не читается: строка запечатана ключом <отпечаток записи>, текущий ключ <отпечаток ключа>
настройка `token` в БД не читается: шифртекст повреждён или принадлежит другой строке
```

Первое сообщение означает, что ключ не задан, второе — что задан другой ключ (названы оба отпечатка), третье — что шифртекст повреждён.
