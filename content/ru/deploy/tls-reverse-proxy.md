Страница объясняет, как клиенты пакетов достигают CRANE по HTTPS и какие условия должен выполнять обратный прокси, чтобы адрес клиента и идентификатор запроса в {{< term "security-journal" >}} были настоящими. Сервер `crane` TLS не завершает: он слушает обычный TCP-порт, а TLS принимает прокси. В поставке это Caddy.

Заголовки `X-Forwarded-For` и `X-Request-Id` сервер принимает только от прокси из списка {{< env "CRANE_TRUSTED_PROXIES" >}}. Если такой прокси пропускает клиентские значения без изменений, клиент подставляет собственный адрес и идентификатор запроса в журнал доступа и аудит. Поэтому раздел [Требования к доверенному прокси](#requirements) обязателен для любого прокси, а не только для Caddy.

## Перед началом {#prerequisites}

- Работающий проект из {{< xref "deploy/docker-compose" >}} или другое развёртывание `crane` за обратным прокси.
- Для Caddy: публичное DNS-имя в {{< env "CRANE_HOST" >}} и свободные порты {{< env "CADDY_HTTP_PORT" >}} и {{< env "CADDY_HTTPS_PORT" >}} на хосте.
- Для другого прокси: известный адрес или подсеть, из которой он подключается к порту API ({{< env "CRANE_HTTP_PORT" >}}).

## Что делает эталонный Caddy {#caddy}

Эталонная настройка лежит в `deploy/caddy/Caddyfile`. Caddy обслуживает ровно одно имя, {{< env "CRANE_HOST" >}}, и проксирует запросы на `crane` по порту {{< env "CRANE_HTTP_PORT" >}} внутри сети `edge`.

- **Сертификат.** Для публичного имени Caddy сам получает сертификат по протоколу ACME. Для `localhost` он использует внутренний центр сертификации Caddy: этот вариант годится для проверки, а не для эксплуатации. Выданные сертификаты лежат в томе `caddy-data`.
- **Порты.** Caddy публикует на хосте порты 80 и 443 (переменные {{< env "CADDY_HTTP_PORT" >}} и {{< env "CADDY_HTTPS_PORT" >}}). Порты `crane` и порт проб на хосте не опубликованы.
- **Публичный адрес.** Compose задаёт серверу {{< env "CRANE_PUBLIC_URL" >}} как `https://` и {{< env "CRANE_HOST" >}}, поэтому ссылки в ответах протоколов ведут на имя, которое обслуживает Caddy.
- **`X-Request-Id`.** Директива `header_up -X-Request-Id` удаляет клиентский заголовок. Сервер не получает чужой идентификатор и выдаёт собственный (UUIDv7).
- **`X-Forwarded-For`.** `Caddyfile` не содержит для него директив. По умолчанию `reverse_proxy` Caddy отбрасывает значения, пришедшие от клиента, и выставляет заголовок сам, с адресом своего пира, то есть клиента ({{< cite "caddy-reverse-proxy" >}}).
- **Список доверенных прокси.** Compose передаёт серверу подсеть `edge` ({{< env "CRANE_EDGE_SUBNET" >}}) как {{< env "CRANE_TRUSTED_PROXIES" >}}. В этой сети только `caddy` и `crane`.

## Требования к доверенному прокси {#requirements}

Любой прокси, адрес которого входит в {{< env "CRANE_TRUSTED_PROXIES" >}}, выполняет все пункты. Требования следуют из того, как сервер выбирает адрес клиента и идентификатор запроса.

1. **Завершает TLS и пересылает запросы на порт API.** Сервер отдаёт API по HTTP. Порт проб ({{< env "CRANE_ADMIN_PORT" >}}) отвечает без токена, поэтому прокси на него не направляется: {{< xref "reference/ports-and-health" >}}.
2. **Удаляет или перезаписывает клиентский `X-Request-Id`.** Сервер принимает значение от доверенного пира, если оно состоит из 1–128 видимых символов ASCII (0x21–0x7E). Прокси, который пропускает клиентское значение, даёт клиенту возможность выбрать идентификатор запроса в журнале. Если заголовка нет или значение недопустимо, сервер выдаёт UUIDv7 сам.
3. **Дописывает адрес своего пира в конец `X-Forwarded-For`.** Сервер объединяет несколько строк заголовка через запятую и читает список справа налево. Он пропускает адреса из {{< env "CRANE_TRUSTED_PROXIES" >}}, и первый чужой адрес считает клиентом. Левые записи подделывает кто угодно, поэтому на результат они не влияют, но запись справа должна принадлежать прокси.
4. **Пишет адреса без порта и без скобок.** Запись вида `203.0.113.9:4000` или `[2001:db8::1]` сервер не разбирает и пропускает.
5. **Соблюдает те же пункты в цепочке.** Если перед прокси стоит ещё один, оба входят в список, и каждый выполняет пункты 2 и 3.
6. **Не ограничивает тело запроса ниже {{< env "CRANE_MAX_PUBLISH_BYTES" >}}.** Иначе публикация получит отказ от прокси, а не `413` от сервера: {{< xref "configure/limits" >}}.

В списке {{< env "CRANE_TRUSTED_PROXIES" >}} перечисляются только адреса прокси. Сети клиентов в него не входят: сервер верит заголовкам каждого адреса из списка.

> [!NOTE]
> Конфигурацию для другого прокси, например nginx, страница не приводит. Поставка содержит только настройку Caddy, а поведение заголовков по умолчанию у каждого прокси своё. Сопоставьте настройки прокси с требованиями выше и проверьте результат по разделу [Проверка](#verify).

## Шаги {#steps}

1. Настройте прокси по разделу [Требования к доверенному прокси](#requirements): TLS, пересылка на порт API, `X-Request-Id`, `X-Forwarded-For`.

2. Задайте публичный адрес: схема `https://` и имя, по которому клиенты обращаются к прокси. Из него строятся ссылки в ответах протоколов.

   ```dotenv
   CRANE_PUBLIC_URL=https://crane.example.com
   ```

3. Задайте адреса прокси: IP-адреса и сети CIDR через запятую. Адрес без префикса означает один хост.

   ```dotenv
   CRANE_TRUSTED_PROXIES=<адрес или CIDR прокси>
   ```

   В Compose-поставке {{< env "CRANE_TRUSTED_PROXIES" >}} выводится из {{< env "CRANE_EDGE_SUBNET" >}}: подсеть `edge` должна содержать адрес прокси и не содержать лишних узлов. Подробнее: {{< xref "deploy/docker-compose#edge" >}}.

4. Перезапустите сервер. Настройки читаются один раз при старте.

## Если прокси нет в списке {#untrusted}

Сервер не отказывает такому прокси в обслуживании. Он считает прокси обычным клиентом и игнорирует оба заголовка.

| Поле | Прокси в списке | Прокси не в списке |
| --- | --- | --- |
| `client_ip` в журнале доступа, `src_endpoint.ip` в аудите | Адрес клиента из `X-Forwarded-For` | Адрес прокси |
| `request_id` в журнале доступа, `metadata.correlation_uid` в аудите | Значение от прокси, если допустимо; иначе UUIDv7 сервера | Всегда UUIDv7 сервера |

В записях видно только прокси: по ним нельзя отличить одного клиента от другого, а `request_id` не совпадает с идентификатором в журнале прокси. Список по умолчанию пуст, поэтому без {{< env "CRANE_TRUSTED_PROXIES" >}} любой прокси попадает в эту строку. Некорректная запись в списке останавливает запуск, сообщение называет переменную: {{< xref "configure/network#errors" >}}.

Обратный случай опаснее: прокси в списке, но не соблюдает требования. Тогда клиент выбирает свой `request_id` (если прокси пропускает `X-Request-Id`) и подставляет в журнал любой адрес (если прокси не дописывает пира в `X-Forwarded-For`). Например, клиент присылает `X-Forwarded-For: 198.51.100.7`, прокси передаёт заголовок без записи справа, и сервер записывает `198.51.100.7` как адрес клиента.

## Проверка {#verify}

1. Отправьте запрос через прокси с собственными заголовками. Запрос без токена получает `401`, но сервер возвращает `X-Request-Id` и в этом ответе.

   ```bash
   curl -sS -D - -o /dev/null \
     -H 'X-Request-Id: probe-from-client' \
     -H 'X-Forwarded-For: 198.51.100.7' \
     https://crane.example.com/cargo/internal/index/config.json
   ```

   В выводе найдите заголовок `x-request-id`. Значение не должно быть `probe-from-client`: у эталонного Caddy это UUIDv7, выданный сервером.

   ```text
   x-request-id: <uuid-v7>
   ```

2. Найдите запись о запросе в журнале `crane` по этому идентификатору. Запись называется «запрос обработан»; поля описаны в {{< xref "security/security-events#access-fields" >}}.

   ```bash
   docker compose --project-directory . \
     -f deploy/compose/docker-compose.yaml logs crane | grep '<uuid-v7>'
   ```

   Поле `client_ip` должно содержать адрес вашего клиента. Если там адрес прокси, его нет в {{< env "CRANE_TRUSTED_PROXIES" >}}. Если там `198.51.100.7`, прокси не дописывает пира в `X-Forwarded-For`: исправьте его настройку до ввода в работу.

3. Убедитесь, что порт проб не опубликован: в колонке `PORTS` вывода `docker compose ps` у `crane` нет портов хоста. Подробности: {{< xref "reference/ports-and-health" >}}.
