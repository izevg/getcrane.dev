CRANE сам отправляет во внешнюю сеть {{< term "egress" "исходящие запросы" >}}: к {{< term "upstream" >}}, фидам уязвимостей, приёмникам webhooks и {{< term "siem" >}}, при импорте и к моделям AI. Весь такой исходящий трафик идёт через один HTTP-клиент с SSRF-guard. Guard отказывает в запросе, если хост не разрешён, схема небезопасна, адрес после DNS не публичный или redirect уводит за разрешённое.

Так {{< term "ssrf" >}} через upstream, DNS или redirect не превращает CRANE в инструмент доступа к внутренней сети и к службе метаданных облака. Каждая выборка и каждый отказ guard попадают в журнал исходящих запросов.

## Угроза {#threat}

SSRF — атака, при которой сервер отправляет запрос на адрес, выбранный атакующим ({{< cite "owasp-ssrf" >}}). Реестру, который ходит во внешние сети по чужим данным, грозят три варианта:

- **Redirect.** Разрешённый хост отвечает `302` на `http://169.254.169.254/` — адрес службы метаданных облака. Клиент, который слепо следует redirect, отправит запрос на внутренний адрес.
- **DNS.** Имя из allowlist резолвится во внутренний адрес: из-за подмены DNS или раздельного DNS внутри сети. Проверка имени не видит, куда оно ведёт.
- **Подмена адресата.** Адрес webhook или приёмника SIEM указывает на внутренний сервис.

## Гарантия {#guarantee}

- Исходящие запросы к upstream идут только на хосты из точного allowlist. Wildcard-хостов нет: каждый upstream перечислен явно.
- Разрешена только схема `https`. Схема `http` допускается лишь явным разрешением в политике; другие схемы отклоняются.
- Каждый адрес, который вернул DNS, проверяется до установки соединения. Если хотя бы один адрес не публичный, отклоняется весь ответ.
- Каждый redirect проходит те же проверки хоста и схемы, что и исходный запрос. Цепочка длиннее 5 redirect не выполняется.
- Для webhooks и приёмников SIEM непубличные адреса запрещены по умолчанию. Исключения задаёт allowlist экземпляра.
- Каждая реальная выборка из upstream, включая отказ guard, записывается в журнал.

## Как это устроено {#mechanism}

### Один клиент для всего {#single-client}

HTTP-клиент для исходящих запросов собирается один раз. Guard встроен в две точки, где клиент сам принимает решения: DNS-резолвер и политика redirect. Публичного способа обойти их нет, а ручную подстановку адресов в обход резолвера CRANE не использует.

### Хост и схема {#host-scheme}

Allowlist хостов нормализуется так же, как проверяемые имена: нижний регистр, без хвостовой точки, без скобок вокруг IPv6. Адрес proxy-репозитория проверяется при сборке конфигурации: схема и хост должны пройти политику, а префикс пути не должен содержать `..`, `?`, `#`, `\` и `:`. Поэтому путь запроса остаётся после имени хоста и не может его сменить. Порт в allowlist не участвует: у upstream бывают нестандартные порты, а хост и адрес проверяются отдельно.

Если в allowlist записан IP-литерал, проверка класса адреса всё равно выполняется: резолва нет, и позже проверять было бы нечего.

### Адрес после DNS {#address}

Проверка стоит между DNS и соединением. Адреса, которые вернул резолвер, проверяются, и именно к ним клиент затем подключается: между проверкой и соединением нет второго резолва.

Один непубличный адрес в ответе отклоняет весь ответ. Молчаливая фильтрация скрыла бы отравленный или раздельный DNS, а это событие для специалиста по безопасности. Ответ DNS без адресов считается сбоем, а не отказом политики: это недоступность, а не попытка атаки.

Непубличными считаются адреса loopback, частных сетей, link-local (в том числе адрес метаданных облака `169.254.169.254`), multicast и ряд зарезервированных диапазонов. Адреса IPv4, вложенные в IPv6 (`::ffff:a.b.c.d`, NAT64, 6to4), оцениваются по вложенному IPv4, поэтому через них правила не обойти.

> [!SECURITY]-
> **Полный перечень непубличных диапазонов**
>
> IPv4: loopback, частные сети, link-local, multicast, broadcast, documentation, `0.0.0.0/8`, `100.64.0.0/10` (CGNAT, включая `100.100.100.200` — метаданные Alibaba Cloud), `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4`.
>
> IPv6: multicast, unique local, link-local unicast, `::/96` (включая `::` и `::1`), `fec0::/10` (site-local), `2001:db8::/32` (documentation), `100::/64` (discard-only), `2001::/32` (Teredo), `64:ff9b:1::/48` (local-use NAT64). Адреса `64:ff9b::/96` (NAT64) и `2002::/16` (6to4) публичны, только если публичен вложенный IPv4.

### Redirect {#redirect}

Каждый redirect-hop проверяется по хосту и схеме так же, как исходный запрос: иначе redirect уводил бы за allowlist. Допускается до 5 redirect. Ответ `3xx` после этого возвращается как есть и считается недоступностью upstream. Redirect без хоста (`data:`, `mailto:`) отклоняется; в журнал отказа попадает только схема, потому что в query бывают подписи и токены.

### Журнал исходящих запросов {#journal}

Каждая реальная выборка из upstream пишется отдельной строкой в {{< term "security-journal" >}} с целью `crane::upstream`. Журнал безопасности не глушится уровнем логов. Поля строки:

| Поле | Значение |
| --- | --- |
| `host` | хост upstream |
| `path` | путь upstream без query |
| `status` | статус ответа, если он получен |
| `failure` | `refused` для отказа SSRF-guard, `unavailable` для сетевой ошибки, `throttled` для ограничения со стороны upstream |
| `elapsed_ms` | время до получения заголовков |

Заголовков, тел и `ETag` в строке нет. Запрос, обслуженный из кэша или присоединившийся к чужой выборке, строки не порождает, поэтому по числу строк с одним `path` видно, сколько раз CRANE реально обращался к upstream. Клиенту при отказе guard уходит только «upstream недоступен» (`502`), правило отказа остаётся в журнале.

## Границы гарантии {#limits}

> [!LIMITS]
> - **Хосты из allowlist доверенные.** Guard не проверяет содержимое ответа разрешённого хоста. Компрометация самого upstream закрывается другими гарантиями: проверкой дайджестов и карантином.
> - **Guard защищает исходящие запросы CRANE, а не сеть вокруг него.** Ограничение сетевого доступа самого процесса (NetworkPolicy в Kubernetes, правила файрвола) остаётся на стороне развёртывания и работает как вторая линия.
> - **Исключения для webhooks и SIEM расширяют доступ.** Каждая запись в allowlist экземпляра разрешает CRANE обращаться к непубличному адресу. Список ведёт администратор развёртывания.
> - **Порт не входит в allowlist.** Допустим любой порт разрешённого хоста.
> - **Отказ guard и сбой различаются.** Ответ DNS без адресов — сбой, а не отказ политики; в журнал он попадает как `unavailable`.
