CRANE принимает людей только через {{< term "oidc" >}}, пакетным клиентам выдаёт собственные токены, а любое действие разрешает политика Cedar при закрытом по умолчанию доступе. Токены выпускает только человек с интерактивной сессией IdP и только сужением своих прав. Опасные операции требуют {{< term "step-up" >}}, а роли устроены так, что администратор платформы не читает журнал, а специалист по мониторингу не публикует пакеты.

Так украденный токен или скомпрометированная роль не дают расширить доступ, а каждое решение об отказе можно объяснить: известно, какое правило сработало.

## Угроза {#threat}

{{< threat summary="Украденный токен, чужой код в задаче и совмещение ролей расширяют доступ — CRANE выпускает токены только людям и лишь сужает права." chips="term:principal, term:separation-of-duties" >}}
{{< threat-what >}}
- **Эскалация через токен.** Скрипт `postinstall` берёт `crp_` из `~/.npmrc` и выпускает себе токен на 90 дней или с более широкими правами.
- **Чужой код в задаче публикации.** Сборка форка или merge request получает токен записи и публикует пакет.
- **Смешение обязанностей.** Администратор платформы, который читает и правит журнал, может скрыть собственные действия.
- **Тихое ослабление защиты.** Владелец команды отключает защитную настройку репозитория, а действие остаётся незамеченным.
- **Лишние права из каталога.** Права выводятся из структуры LDAP по догадке и расходятся с намерением организации.

## Гарантия {#guarantee}

- Люди входят только через OIDC. Прямого подключения LDAP, Active Directory и SAML нет: такие каталоги подключаются через федерирующий OIDC-провайдер.
- Каждый запрос проходит авторизацию, доступ закрыт по умолчанию. Решение несёт trace: какое правило сработало.
- Токен выпускает только человек со своей интерактивной сессией IdP. Токены CRANE и учётные данные сервисных аккаунтов ничего не выпускают (`403 interactive-login-required`).
- Выпуск только сужает права: новый токен не шире прав человека (`403 scope-exceeds-principal`).
- Токен записи существует только в задаче публикации без чужого кода и выдаётся только для защищённых ref.
- Опасные операции требуют свежей многофакторной аутентификации.
- Администратор платформы и специалисты `secops` и `auditor` — несовместимые роли: в режиме `strict` вход с обеими ролями не активирует доступ к журналу и порождает событие `sod.violation`.

## Как это устроено {#mechanism}

### Люди только через OIDC {#oidc}

OIDC-провайдер отвечает на вопрос «кто это», CRANE — на вопрос «что ему можно». CRANE принимает любого провайдера со стандартным OIDC (discovery, JWKS). Роли и группы приходят из токена, а в права превращаются только явным отображением групп на команды и роли: структура каталога сама права не выдаёт.

> [!SECURITY]-
> **Почему не LDAP, Active Directory и SAML напрямую**
>
> - Прямой bind означает, что CRANE принимает пароли и хранит привилегированную учётную запись для поиска. Реестр на пути сборки стал бы держателем секретов.
> - В LDAP нет `acr`, `amr`, `auth_time`, WebAuthn и passkeys. Модель опасных действий со свежим MFA была бы невыполнима.
> - Деревья OU и групп в корпоративных каталогах непоследовательны. Права, выведенные из них, избыточны и дрейфуют незаметно.
> - LDAP-инъекции известны, а AD — главная цель при боковом перемещении. Реестр не должен быть ещё одним местом ввода этих учётных данных.
>
> Поддерживаемый путь: перед каталогом стоит Keycloak или другой OIDC-провайдер, SAML подключается через identity brokering. Адаптеров и плагинов LDAP и SAML нет.

### Токены для клиентов {#tokens}

Пакетные менеджеры не проходят OIDC-вход, поэтому CRANE выдаёт им токены `crp_`, `crr_`, `crci_`, привязанные к принципалу. Права в токен не зашиваются: каждый запрос заново проходит авторизацию по текущим ролям, поэтому изменение ролей действует без перевыпуска. Хранение и формат токенов: {{< xref "features/security/secrets" >}}.

### Выпуск только человеком и только сужением {#issuance}

1. Токены выпускает человек, который вошёл в IdP в этой сессии (cookie консоли или JWT, полученный входом пользователя и его продлением). Иначе скрипт с `crp_` выпустил бы себе личный токен на 90 дней.
2. Выпуск сужает: scopes нового `crp_` не шире текущих прав человека, робот получает ровно свои scopes, `crci_` не шире trust policy.
3. Личный долгоживущий токен и секрет робота выпускаются только со step-up. Сессионный `crp_` step-up не требует, но живёт не дольше 12 часов и не дольше сессии IdP: иначе пришлось бы подтверждать MFA каждые 12 часов, а CRANE стал бы недоступен при IdP без step-up.
4. Обмен ID token платформы выпускает только `crci_`, причём только по токену доверенного внешнего издателя. Токены CRANE как исходный токен не принимаются.

### Фаза публикации в CI {#ci-phase}

Токен записи существует только в задаче публикации, где не исполняется чужой код. Сборка и установка зависимостей идут в отдельной задаче без токена записи, с отключёнными скриптами установки. Запись разрешена только из защищённого ref вне merge request и форка; остальные получают токен только для чтения. Scope `publish` ограничен именами из правила trust policy. Каждая публикация получает provenance из claims токена платформы, а не из слов клиента.

### Cedar и default deny {#cedar}

Авторизацию считает политика Cedar по ролям из таблицы членства, а не по токену IdP: токен IdP только наблюдается. Доступ закрыт по умолчанию. Решения кэшируются на 30 секунд с привязкой к эпохе принципала, поэтому отзыв прав действует на всех репликах быстро.

### Объяснимый отказ {#explainable}

Каждое решение несёт trace: какие политики сработали и почему. Закрытый от пользователя пакет протокол отдаёт как несуществующий (`404`), чтобы не раскрывать его наличие. Причину видно по идентификатору запроса через диагностику (`GET /api/v1/diagnostics/{request_id}`, команда `cctl diag`). Ответ об ошибке содержит `rule_id`, `request_id` и подсказку по исправлению.

### Step-up для опасных операций {#step-up}

{{< term "step-up" >}} — повторный вход со свежим MFA. Его требуют действия, которые ослабляют защиту, выпускают долгоживущий секрет, раскрывают персональные данные или снимают блокировку:

- персональные данные в журнале и экспорт журнала;
- исключения, экстренная блокировка и её снятие, VEX;
- роботы, их секреты, личные долгоживущие токены и trust policies;
- защитные настройки репозитория, webhooks и приёмники SIEM;
- политики и gates, выпуск из карантина, применение retention.

Если IdP не передаёт `auth_time`, свежесть MFA подтвердить нельзя, и опасные действия недоступны. Точный перечень — флаги `x-crane-step-up` в описании API.

### Роли и разделение обязанностей {#roles}

| Роль | Уровень | Главное, что может | Чего не может |
| --- | --- | --- | --- |
| `reader` | команда | Искать, читать, устанавливать | Публиковать |
| `developer` | команда | Публиковать в dev и snapshot | Публиковать в release, менять настройки |
| `maintainer` | команда | Публиковать в release своих namespaces | Выдавать исключения по безопасности |
| `owner` | команда | Роли, роботы и trust policies команды | Читать журнал, менять политики безопасности |
| `appsec` | экземпляр | Политики, исключения, экстренная блокировка | Читать журнал целиком |
| `secops` | экземпляр | Журнал, приёмники SIEM, отзыв токенов | Публиковать, удалять пакеты, менять платформу |
| `auditor` | экземпляр | Журнал только на чтение, маскированный | Раскрывать данные, что-либо менять |
| `platform-admin` | экземпляр | Хранилища, upstream, интеграции, команды | Читать журнал, менять политики безопасности |

Разделение обязанностей держится на четырёх правилах:

- **Администратор не контролирует журнал.** Роли `platform-admin` и `secops`, а также `platform-admin` и `auditor` несовместимы у одного человека.
- **Журнал не изменяет никто.** Запись идёт через роль базы данных без прав на изменение и удаление: {{< xref "features/security/security-journal" >}}.
- **Экспорт в SIEM нельзя тихо выключить.** Приёмники меняет только `secops`, и событие об изменении уходит в SIEM до применения.
- **Защитные настройки меняет отдельная операция со step-up**, а не владелец команды.

### Команды {#teams}

Единица владения и членства — {{< term "workspace" "команда" >}}. Роли в команде выдаёт только явное отображение группы IdP, которое ведёт администратор платформы со step-up, либо локальное членство, которое можно запретить настройкой экземпляра. Подробности: {{< xref "features/registry/teams-and-ownership" >}}.

## Границы гарантии {#limits}

> [!LIMITS]
> - **Без каталога и push роль, снятая в IdP, живёт до следующего входа.** CRANE узнаёт об изменении при входе, обмене или продлении токена. Пока ни каталога, ни push нет, срок ограничивает потолок сессионного токена: по умолчанию 1 час вместо 12. Отключённый в IdP пользователь теряет доступ не позже этого срока или истечения refresh. Для Keycloak включаются опрос каталога и admin events, для остальных провайдеров — SCIM. Отчёт о пересмотре доступа показывает «наблюдалось в момент», а не текущее состояние IdP.
> - **Качество сигнала MFA определяет IdP.** Если провайдер не передаёт `acr`, `amr` и `auth_time`, свежесть MFA вычислить нельзя. Тогда либо опасные действия недоступны, либо администратор явно заявляет, что IdP требует MFA на каждом входе.
> - **Большие списки групп не применяются.** Если IdP не вместил группы в токен, роли из токена не меняются. Это безопасно, но права не обновятся до исправления источника групп.
> - **Совместимость ролей проверяется в строгом режиме.** Режим предупреждения допускается только явной настройкой для профиля, где всё обслуживает один человек; в консоли тогда постоянный баннер.
> - **Окно применения отзыва.** Отзыв токена или блокировка применяются на всех репликах обычно за 5 секунд и не позже чем за 30.
> - **Политика остаётся на стороне организации.** CRANE закрывает доступ по умолчанию, но ошибочно выданная роль или лишний `group_mapping` дают права, которые политика разрешает.
> - **Смена IdP создаёт новых принципалов.** Люди из нового провайдера не склеиваются с прежними.
