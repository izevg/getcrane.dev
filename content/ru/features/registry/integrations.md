CRANE открыт для автоматизации четырьмя путями: REST API с описанием OpenAPI, подписанные webhooks, обмен токена CI на краткоживущий credential и протокол A2A для внешних агентов. Все они работают от имени {{< term "principal" "принципала" >}} и проходят ту же авторизацию, что и консоль.

Главный принцип интеграций: секрет, которого нет, нельзя украсть. Поэтому для CI CRANE предпочитает обмен токена платформы долгоживущему паролю. Страница описывает каждый путь и устройство обмена токена. Настройку идентификации в текущем развёртывании описывает страница {{< xref "configure/identity" >}}.

## REST API {#api}

API доступен под префиксом `/api/v1` и описан спецификацией OpenAPI 3.1. Консоль, CLI и внешние скрипты вызывают этот API.

- **Версионирование.** Мажорная версия входит в путь. Устаревание объявляется заголовком `Sunset` не менее чем за 6 месяцев.
- **Ошибки.** Ошибки имеют формат `application/problem+json` ({{< cite "rfc-9457" >}}) с полями `rule_id`, `request_id` и `remediation`. Каждый ответ несёт заголовок `X-Request-Id`, по которому видна диагностика ({{< xref "features/registry/cli#diag" >}}).
- **Идемпотентность.** Все изменяющие запросы принимают заголовок `Idempotency-Key`. Ключ хранится 24 часа вместе с хэшем запроса и действует в пределах принципала. Ответы с секретом не сохраняются: повтор возвращает `409` без секрета и со ссылкой на ресурс, потому что секрет показывается один раз.
- **Списки.** Пагинация курсорами, фильтры в параметрах запроса, частичные ответы через `fields`.
- **Ресурсы.** Ответы содержат ссылки на допустимые действия. Клиент строит интерфейс по ним, а не по собственным правилам ({{< xref "features/registry/console" >}}).
- **Аутентификация.** Консоль использует cookie-сессию. CLI и скрипты передают `Authorization: Bearer` с JWT провайдера или токеном CRANE.

## Токены для автоматизации {#tokens}

Права в токен не зашиваются: каждый запрос проходит авторизацию по текущим ролям. Тип токена виден по префиксу, поэтому сканеры секретов и SIEM отличают их.

| Токен | Выпускает | Срок | Предъявляет |
| --- | --- | --- | --- |
| `crp_` личный | CRANE по интерактивной сессии IdP человека | Сессионный: 12 часов; личный долгоживущий: до 90 дней по политике | Пакетные менеджеры разработчика |
| `crr_` робота | CRANE по решению владельца команды | Обязательный срок, до 90 дней; ротация с перекрытием 24 часа | Сервисы и сборки без workload identity |
| `crci_` задачи | CRANE в обмен на токен платформы | По умолчанию 15 минут, со scope записи 5 минут, не больше часа и не дольше задачи | GitLab CI, Kubernetes, сервисные аккаунты |

Токены `crp_` и `crr_` выпускает только человек в своей интерактивной сессии IdP; токен `crci_` выдаётся только обменом. Токен CRANE и JWT сервисного аккаунта ничего не выпускают. Новый токен не может быть шире прав выпускающего. Подробнее о правилах выпуска, шифровании и хранении: {{< xref "features/security/secrets" >}} и {{< xref "features/security/access-control" >}}.

Системам без OIDC владелец команды создаёт робота в консоли: имя, команда, права (репозитории, namespace, действия) и обязательный срок. Токен `crr_` показывается один раз. Для ротации CRANE заранее выпускает второй секрет, оба действуют 24 часа, затем старый отзывается. Неиспользуемые роботы подсвечиваются через 30 дней и предлагаются к отзыву через 90. Создание робота и ротация секрета требуют интерактивной сессии IdP и {{< term "step-up" >}}.

## Обмен токена CI на краткоживущий токен {#oidc-exchange}

Задача CI предъявляет CRANE токен своей платформы, а CRANE выдаёт токен `crci_` на время задачи. Секрет в CI не хранится.

```mermaid {caption="Рисунок 1. Обмен токена платформы на краткоживущий токен. Права определяет trust policy, а не запрос."}
sequenceDiagram
  autonumber
  participant J as Задача CI
  participant C as CRANE
  participant I as Издатель токена<br>(GitLab, Kubernetes, другие)
  J->>C: ID-токен платформы (aud: crane)
  C->>I: Ключи издателя (JWKS)
  C->>C: Проверка подписи, iss, aud, exp и trust policy
  C-->>J: Токен crci_ с правами из trust policy
  J->>C: Публикация пакета с токеном crci_
```

CRANE проверяет подпись токена по ключам издателя, значения `iss`, `aud`, `exp` и `nbf`, затем сопоставляет claims с trust policy. Trust policy перечисляет издателя, допустимые claims (проект, namespace, ветку, имя сервисного аккаунта) и права; проекты в ней указываются явно, а не маской. Для GitLab запись доступна только из защищённой ветки или тега: конвейеры merge request и форки получают только чтение, а право публикации ограничено именами из trust policy.

Запрос делается по {{< cite "rfc-8693" >}}: `POST /api/v1/tokens/exchange` принимает токен платформы как `subject_token` и выдаёт только `crci_`. Токены CRANE в качестве `subject_token` не принимаются. Тот же обмен обслуживает любого доверенного издателя: projected ServiceAccount token Kubernetes, GitHub Actions, сервисный аккаунт Keycloak.

Каждая публикация из CI получает {{< term "provenance" >}} из claims токена, а не из того, что сообщил клиент: проект, коммит, конвейер, задача, ветка и признак защищённости ветки. Эта provenance выпущена CRANE, а не подписана сборочной платформой, поэтому сама по себе не означает SLSA Build L2 ({{< cite "slsa" >}}); такой уровень дают attestations из CI. Подробнее: {{< xref "features/security/evidence-and-scanning" >}}.

## Шаблоны GitLab CI {#ci-templates}

Для GitLab CRANE поставляет готовые шаблоны CI. Сборка и публикация разделены на две задачи.

```yaml
# .gitlab-ci.yml
include: { project: <group>/crane-ci, file: npm.yml }

build:
  extends: .crane-npm-build        # npm ci --ignore-scripts, сборка; без id_tokens и без токена записи
publish:
  extends: .crane-npm-publish      # зависимости не ставит: берёт артефакт сборки
  needs: [build]
  id_tokens:
    CRANE_ID_TOKEN: { aud: crane }
  rules: [{ if: $CI_COMMIT_TAG }]  # только защищённые теги
```

Задача публикации обменивает ID-токен на `crci_`, записывает конфигурацию клиента без секрета в логах, публикует пакет и прикладывает {{< term "sbom" >}} в CycloneDX и provenance.

Разделение сделано намеренно. `id_tokens` в GitLab задаются на задачу, поэтому токен записи существует только в задаче публикации, где не исполняется чужой код. Зависимости ставятся с `--ignore-scripts` (для pip — с `--only-binary :all:`, где возможно; build-скрипты cargo исполняются в задаче сборки без токена), а задача публикации их не ставит. Условия записи и состав provenance описаны выше.

## Webhooks {#webhooks}

CRANE отправляет события в подписанных webhooks. Доставка надёжна, потому что событие записывается в таблицу outbox в той же транзакции, что и изменение: событие появляется тогда и только тогда, когда транзакция завершилась.

- **Доставка.** Воркер выбирает события пачками, создаёт доставки по подпискам и помечает событие обработанным.
- **Подпись.** Заголовок `Crane-Signature: t=<unix>,v1=HMAC-SHA256(secret, t + "." + body)` позволяет получателю проверить отправителя. Заголовок `Crane-Event-Id` позволяет отбросить повторную доставку.
- **Повторы.** При ошибке CRANE повторяет доставку с экспоненциальной задержкой и случайным разбросом от 10 секунд до 1 часа в течение 24 часов. Затем событие попадает в очередь недоставленных (DLQ), откуда его можно повторить вручную из консоли.
- **Секрет и адреса.** Секрет подписи показывается один раз. Адреса получателей проходят проверку исходящих запросов ({{< xref "features/security/egress-guard" >}}).

Outbox служит только внешней доставке (webhooks и {{< term "siem" >}}); внутренние задачи идут через очередь заданий.

### Каталог событий {#events}

| Событие | Когда |
| --- | --- |
| `version.published`, `version.promoted`, `version.blocked`, `version.deleted` | Жизненный цикл версии |
| `security.finding.created`, `security.finding.resolved`, `security.finding.priority_changed` | Новые, закрытые и переприоритизированные уязвимости |
| `security.advisory.emergency`, `security.emergency_block.applied`, `security.emergency_block.lifted` | Экстренный режим |
| `security.vex.created`, `security.sla.breached` | VEX-заявление; нарушение срока устранения |
| `feed.lagging`, `feed.recovered` | Отставание и восстановление фида уязвимостей |
| `license.violation`, `license.review_required` | Решения лицензионной политики |
| `exception.expiring`, `exception.expired` | Исключения с TTL |
| `credential.expiring`, `credential.revoked` | Роботы и токены |
| `quota.threshold`, `upstream.unavailable` | Эксплуатация |

## SIEM и SOAR {#siem}

События безопасности уходят в {{< term "siem" >}} в схеме {{< term "ocsf" >}} по syslog поверх TLS, HTTP или OTLP. Доставка идёт по принципу «не менее одного раза» с курсором на каждый приёмник и идентификатором события, поэтому при недоступности SIEM события копятся и не теряются. Платформа SOAR получает события через webhooks и выполняет ответные действия через REST от имени робота `soar` с ограниченными правами; все действия идемпотентны и попадают в журнал. Подробнее: {{< xref "features/security/security-journal" >}}.

## A2A-агент {#a2a}

CRANE предоставляет внешним агентам (ассистентам организации, агентам команд, CI-ботам) диалоговый интерфейс по протоколу A2A вместо набора вызовов REST. Агент работает внутри роли `serve` и не имеет собственного хранилища и обходных путей: он вызывает те же сценарии, что и REST.

- **Идентичность.** Каждый вызов выполняется от имени принципала, и права агента не шире прав принципала.
- **Чтение.** Навыки поиска пакетов, карточки пакета и версии, находок, анализа влияния, объяснения решения и проверки готовности к офлайну.
- **Запись.** Только обратимые действия с метаданными: пометка версии устаревшей, запрос approval, исключение с TTL, создание задачи и подписка на webhook. Публикация, удаление, продвижение, изменение политик и ролей через агента не выполняются.
- **Подтверждение.** Агент формирует план и ничего не меняет, пока человек не подтвердит его кнопкой в консоли. Повторный вызов агентом план не подтверждает.

Если языковые модели недоступны, навыки чтения возвращают структурированные данные, а REST и консоль работают без агента. Границы использования ИИ описаны на странице {{< xref "features/security/ai-boundaries" >}}.
