`cctl` — консольный клиент CRANE. Он входит в систему через провайдера {{< term "oidc" >}}, выпускает токен для пакетных менеджеров и записывает его в их конфигурацию, а также выполняет операции администрирования и диагностики. Разработчику хватает двух команд: `cctl login` и `cctl setup`.

Пакетные менеджеры не умеют проходить OIDC-вход, поэтому CRANE выдаёт им собственные токены, привязанные к личности из IdP. `cctl` автоматизирует этот путь: человек входит один раз, остальное делает клиент. Название `cctl` отличает консольный клиент от одноимённой утилиты `crane` из экосистемы контейнерных реестров.

## Вход {#login}

Команда `cctl login` получает у провайдера access- и refresh-токены. Способ входа зависит от возможностей IdP.

```mermaid {caption="Рисунок 1. Выбор способа входа. Вставка кода из браузера другого устройства не поддерживается."}
flowchart TB
  start["cctl login"]
  device{"IdP поддерживает<br>device flow?"}
  dev["Device flow:<br>код и ссылка в терминале"]
  loop["Loopback Authorization Code + PKCE<br>на 127.0.0.1, случайный порт"]
  browser{"На машине есть браузер?"}
  token["Личный токен из консоли:<br>cctl login --token"]
  start --> device
  device -- "да" --> dev
  device -- "нет" --> browser
  browser -- "да" --> loop
  browser -- "нет" --> token
```

- **Device flow.** Если у IdP есть device flow ({{< cite "rfc-8628" >}}), CLI показывает код и ссылку, а человек входит в IdP с MFA по политике провайдера. Подходит для сервера без браузера и для IDE.
- **Loopback и PKCE.** Иначе CLI открывает браузер и принимает ответ на `127.0.0.1` со случайным портом ({{< cite "rfc-8252" >}}, {{< cite "rfc-7636" >}}).
- **Без браузера.** Если браузера нет, а device flow недоступен, личный токен выпускается в веб-консоли, и `cctl login --token` принимает его.

Refresh-токен CLI хранит в системном хранилище секретов: Keychain, Secret Service или Credential Manager. Команда `cctl login --refresh` выпускает новый токен без повторного ввода пароля, пока жива сессия IdP. Когда сессия закончилась, нужен новый вход.

## Настройка пакетных менеджеров {#setup}

`cctl setup <клиенты>` выпускает сессионный токен `crp_` и записывает его в конфигурацию каждого клиента. Токен живёт 12 часов, ограничен запрошенными правами, например только чтением или конкретными командами, и показывается один раз. Секрет не попадает в историю shell и в файлы проекта.

```bash
cctl setup npm pip maven gradle nuget cargo
```

`cctl setup` настраивает два источника: hosted и proxy. Порядок источников не важен: безопасность держит инвариант имён ({{< xref "features/security/namespace-reservation#no-groups" >}}).

| Клиент | Куда `cctl` записывает токен | Как клиент его передаёт |
| --- | --- | --- |
| npm, pnpm, yarn | `~/.npmrc` | Заголовок `Authorization: Bearer` |
| pip, uv, poetry | `~/.netrc` или keyring для хоста CRANE | Basic: пользователь `__token__`, пароль — токен |
| Maven | `~/.m2/settings.xml`, элемент `<server>` | Basic: пользователь `token`, пароль — токен |
| Gradle | `~/.gradle/gradle.properties` | Basic или заголовок через `credentials(HttpHeaderCredentials)` |
| dotnet, NuGet | credential provider `crane`, он выдаёт токен по запросу и сам продлевает его через CLI | Basic |
| cargo | `~/.cargo/config.toml` и credential provider; токен лежит в системном хранилище | Заголовок `Authorization` с токеном без префикса схемы |

В CI токен клиенту передают штатным способом самого клиента, но предпочтителен обмен токена платформы, который не требует хранимого секрета ({{< xref "features/registry/integrations#oidc-exchange" >}}).

## Команды {#commands}

| Команда | Что делает |
| --- | --- |
| `cctl login` | Вход в CRANE; `--token` принимает личный токен, `--refresh` продлевает токен, `--team <slug>` выбирает команду атрибуции |
| `cctl setup <клиенты>` | Выпускает сессионный токен и настраивает клиентов |
| `cctl tokens` | Список токенов пользователя и их отзыв |
| `cctl robots` | Роботы команды: создание, выпуск и ротация секрета, отключение |
| `cctl publish` | Публикация версии |
| `cctl promote` | Продвижение версии к релизу |
| `cctl diag <request-id>` | Объяснение отказа или ошибки по идентификатору запроса |
| `cctl readiness` | Отчёт о готовности lockfile или SBOM к офлайну |
| `cctl warm` | Прогрев кэша по lockfile или SBOM |
| `cctl export` | Экспорт журнала и отчётов |
| `cctl audit downloads` | Запрос «кто скачал версию» за период (роль SecOps) |

Токены CRANE и токен сервисного аккаунта ничего не выпускают: токены выпускает только человек в интерактивной сессии IdP ({{< xref "features/security/access-control" >}}). Опасные операции, такие как создание робота и выпуск его секрета, требуют {{< term "step-up" >}}: CLI запускает повторный вход с MFA, когда получает отказ с требованием более сильной аутентификации.

## Диагностика отказа {#diag}

Протокол пакетного менеджера не различает «нет прав» и «нет пакета»: клиент получает нейтральный `404`. Причина видна по идентификатору запроса, который каждый ответ несёт в заголовке `X-Request-Id`.

```bash
cctl diag <request-id>
```

Команда запрашивает диагностику и состояние системы. В ответе видны причина отказа, сработавшее правило и контакт, к кому обратиться. Трассу политик видит только тот, кто вправе видеть это событие; чужой или скрытый идентификатор получает нейтральный `404`. Тот же ответ доступен в консоли ({{< xref "features/registry/console#s-states" >}}).

## Команда атрибуции {#team}

Человек из нескольких команд выбирает команду, на которую относятся скачивания по токену: `cctl login --team <slug>`. Для `cctl setup` команда выбирается так же. Нужны разные команды — нужны разные токены ({{< xref "features/registry/teams-and-ownership#attribution" >}}).
