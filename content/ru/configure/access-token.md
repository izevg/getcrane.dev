Страница описывает, как задать токен, которым защищён доступ ко всем репозиториям CRANE. Токен статический: администратор развёртывания создаёт его сам и передаёт серверу в {{< env "CRANE_TOKEN" >}} или в файле {{< env "CRANE_TOKEN_FILE" >}}. Сервер хранит в памяти только SHA-256 токена и сравнивает дайджесты, поэтому время проверки не зависит от длины предъявленного значения.

Токен один на весь экземпляр: он открывает все репозитории всех форматов, на чтение и на запись. Анонимного доступа к протоколам нет. Роли и права у токена не различаются.

## Перед началом {#prerequisites}

- Способ передать файл секрета процессу: том Docker, секрет Kubernetes. Для Compose: {{< xref "deploy/docker-compose#secrets" >}}.
- Команда `openssl` для примера ниже; подойдёт любой генератор случайных значений.

## Шаги {#steps}

1. Создайте случайное значение и сохраните его в файле. Значение — любая непустая строка; перевод строки в конце файла сервер отбрасывает, пробелы внутри сохраняет. Процесс сервера должен иметь право читать файл.

   ```bash
   umask 077
   openssl rand -hex 32 > ./secrets/crane_token
   ```

2. Передайте серверу путь к файлу. Токен задаётся ровно одним способом: {{< env "CRANE_TOKEN" >}} вместе с {{< env "CRANE_TOKEN_FILE" >}} дают ошибку запуска.

   ```dotenv
   CRANE_TOKEN_FILE=/run/secrets/crane_token
   ```

3. При необходимости задайте имя {{< term "principal" "принципала" >}}, от имени которого сервер выполняет запросы с этим токеном. Значение по умолчанию — `crane`. Имя попадает в {{< term "security-journal" >}} (аудит и журнал доступа) и в ответ `owners` для Cargo. Оно не может быть пустым и не может содержать управляющие символы; пробелы по краям отбрасываются.

   ```dotenv
   CRANE_TOKEN_PRINCIPAL=ci-platform
   ```

4. Перезапустите сервер. Токен читается один раз при старте, поэтому смена значения вступает в силу после перезапуска.

## Проверка {#verify}

Запрос без заголовка авторизации получает `401` с описанием схемы входа. Запрос с неверным токеном получает `403`. Запрос с верным токеном проходит:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://crane.example.com/cargo/internal/index/config.json
```

```text
401
```

```bash
printf 'header = "Authorization: %s"\n' "$(cat ./secrets/crane_token)" \
  | curl -sS -o /dev/null -w '%{http_code}\n' -K - https://crane.example.com/cargo/internal/index/config.json
```

```text
200
```

Токен передаётся через stdin (`-K -`), поэтому он не виден в списке процессов.

## Как клиенты предъявляют токен {#presenting}

Формат определяет, в каком заголовке и в какой схеме клиент присылает токен. Сейчас сервер обслуживает Cargo и npm.

| Формат | Заголовок и схема |
| --- | --- |
| Cargo | `Authorization: <token>` без схемы |
| npm | `Authorization: Bearer <token>` |

Чужая схема не принимается «как есть»: заголовок с другой схемой считается неверным токеном. Отказ из-за неверного токена записывается в аудит с результатом «токен отвергнут». Запрос без заголовка — часть рукопожатия протокола, он не аудируется. Успешный вход отдельным событием аудита не фиксируется; имя принципала видно в журнале доступа.

> [!SECURITY]-
> Токен защищает протоколы пакетов. Порт проб (admin) отвечает без токена, поэтому его не публикуют: {{< xref "reference/ports-and-health" >}}. Файл TOML хранит значения открытым текстом, поэтому передавайте токен ключом `token_file`, а не `token`.
